Option 1 · Browser extension Recommended · no command line · all platforms

The extension copies the muse.ai session that is already logged in on your own computer to this server. No Python, no terminal, no commands.

Why an extension? Both required muse.ai cookies are marked httpOnly, so page scripts (typing document.cookie in the F12 console, or a bookmarklet) cannot read them. Only the browser extension cookies API can.

1
Download and unzip the extension

Unzip it into a folder you will keep, for example D:\muse2api-extension.

Download muse2api-extension.zip
2
Load the unpacked extension in your browser

Chrome is shown below; Edge, Brave, Vivaldi and other Chromium browsers work the same way.

  1. Type chrome://extensions in the address bar and press Enter
  2. Turn on Developer mode in the top right corner
  3. Click Load unpacked in the top left corner
  4. Select the folder you unzipped in step 1 (the folder itself, not a single file inside it)
3
Log in to muse.ai, then import from the extension popup

Open https://muse.ai/ in that browser and log in until you can see the chat screen. Then click the extension icon in the toolbar, paste the two values below and press the import button.

4
Check the Account Pool and repeat every ~2 days

The imported account appears in the Account Pool tab. When its status shows Error, Missing core, or the Expires column shows Expired, repeat step 3. Sessions last about two days, so plan to re-import roughly every other day.

Option 2 · Manual copy from the Network panel No install · fallback

If you do not want to install the extension you can copy the cookie string by hand. Use the Network panel request headers, not the Console — the cookie: request header includes the httpOnly cookies that the Console cannot see.

  1. Open https://muse.ai/ in your own browser and log in; stay on the chat screen
  2. Press F12 to open developer tools and switch to the Network tab
  3. Press F5 to reload the page so the request list fills up
  4. Click any muse.ai request in the list (the first one is fine)
  5. On the right, open Headers and scroll to Request Headers
  6. Find the line that starts with cookie: and copy everything after the colon (starting at hatch_sess=)
  7. Paste it into the import box below and click Import

Make sure you copy the request header, not a response set-cookie header — response headers only contain some of the cookies.

Option 3 · Paste an import or use the built-in helper Advanced

Already have a cookie string (including one copied in option 2)? Paste it here.

The binary ships a helper that opens its own browser window, lets you log in to muse.ai, reads the cookies and uploads them here automatically. Run it on a machine that can reach this server: 

muse2api cookie-helper --base <BASE-URL> --key <KEY> --label muse-01

The command refreshes automatically once the API key is loaded; --base is this server's URL without the /v1 suffix. Read the full usage document or download it.

Cookie lifetimes Measured

Observed lifetimes of the muse.ai cookies (they differ slightly per account):

CookieRequiredObserved lifetimeRole
hatch_sess Required ~30 days Main session — decides whether you can log in
hatch_vml Required ~2 days Short-lived validation token — decides the account lifetime
hatch_gw Optional ~1 year Gateway routing cache, not needed for login
hatch_native_auth_device Optional ~30 days Device identifier — not a login credential

How long does an account really live? As long as its earliest-expiring required cookie, which is hatch_vml — about 2 days.
That two-day window is not extended by heavy use. The service does read newly issued muse.ai cookies back into the account pool after each generation (so the Expires column keeps updating), but the expiry of the required cookies is not pushed back.
So re-import roughly every two days. It takes seconds with the extension.
Import several accounts at once: the pool rotates by least-recently-used, so more accounts mean better stability and you can stagger the re-imports (one account a day instead of all of them at once).
When must you re-import? When Expires shows Expired, when the status shows Error, or when the Missing core badge appears.

        These are the three real Muse capabilities: Muse Spark (language / code), Muse Image
        (image generation) and Muse Video (video generation). The muse.ai web app routes automatically and has
        no model selector, so model only exists for downstream compatibility.
        Model aliases are accepted: common names such as gpt-4o, gpt-5,
        claude-sonnet-4, deepseek-chat or gemini-2.5-pro are mapped onto the
        matching capability, and an unknown name is passed through unchanged.
      


      
2. Setup

      
export MUSE2API_BASE="http://your-host:18610"
export MUSE2API_KEY="m2a_your_api_key"


      
3. Chat and code (curl)

      
# Non-streaming
curl -sS "$MUSE2API_BASE/v1/chat/completions" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"muse-spark","messages":[{"role":"user","content":"Write a quicksort in Python"}]}'

# Streaming: add "stream":true. The response is standard SSE
# ("data: {...}" frames terminated by "data: [DONE]").
curl -N "$MUSE2API_BASE/v1/chat/completions" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"muse-spark","stream":true,"messages":[{"role":"user","content":"Explain async/await"}]}'


      
4. Images (curl)

      
# Synchronous generation
curl -sS "$MUSE2API_BASE/v1/images/generations" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"muse-image","prompt":"A shiba inu in an astronaut helmet","size":"1:1","response_format":"url"}'

# Response
# {"created":1790148495,"data":[{
#   "revised_prompt":"A shiba inu in an astronaut helmet",
#   "url":"http://your-host:18610/v1/media/xxxx.webp",
#   "size":"1:1","kind":"image","bytes":23860}]}
#
# The url is absolute, so downstream clients can render or download it directly.
# Add "response_format":"b64_json" to receive base64 instead of a link.

# Asynchronous image task (for clients that want a job id)
curl -sS -X POST "$MUSE2API_BASE/v1/images/tasks" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"A shiba inu in an astronaut helmet","size":"1:1","timeout":600}'
# -> 202 {"id":"img_task_...","status":"queued","progress":0}

curl -sS "$MUSE2API_BASE/v1/images/tasks/<ID>" -H "Authorization: Bearer $MUSE2API_KEY"
# -> status completed, plus {"created":...,"data":[{"url":"...","kind":"image","bytes":...}]}


      
5. Videos (curl, asynchronous)

      
# 1) Create the job
curl -sS -X POST "$MUSE2API_BASE/v1/videos" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"muse-video","prompt":"An orange kitten walking on grass","duration":5,"size":"16:9"}'
# -> {"id":"vid_...","status":"queued","progress":0}

# 2) Poll until the status is completed or failed
curl -sS "$MUSE2API_BASE/v1/videos/<ID>" -H "Authorization: Bearer $MUSE2API_KEY"
# -> {"status":"completed","url":"/v1/media/xxxx.mp4",
#     "result":{"url":"http://your-host:18610/v1/media/xxxx.mp4","bytes":1234567}}

# Status values: queued -> processing -> completed | failed.
# On failure the task carries a human readable "error".


      
6. Python (OpenAI SDK compatible)

      
import time

import requests
from openai import OpenAI

BASE = "http://your-host:18610"
KEY = "m2a_your_api_key"

# point the SDK at this gateway
client = OpenAI(base_url=BASE + "/v1", api_key=KEY)

# chat
reply = client.chat.completions.create(
    model="muse-spark",
    messages=[{"role": "user", "content": "Write a quicksort in Python"}],
)
print(reply.choices[0].message.content)

# streaming
stream = client.chat.completions.create(
    model="muse-spark",
    messages=[{"role": "user", "content": "Explain async/await"}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="", flush=True)

# images
image = client.images.generate(
    model="muse-image",
    prompt="A shiba inu in an astronaut helmet",
    size="1:1",
)
print(image.data[0].url)

# videos use the native asynchronous endpoint
headers = {"Authorization": "Bearer " + KEY}
task = requests.post(
    BASE + "/v1/videos",
    headers=headers,
    json={"prompt": "An orange kitten walking on grass", "duration": 5, "size": "16:9"},
    timeout=60,
).json()

while True:
    state = requests.get(BASE + "/v1/videos/" + task["id"], headers=headers, timeout=60).json()
    if state.get("status") in ("completed", "failed"):
        break
    time.sleep(4)

print(state)

8. Authentication

      

        Every endpoint except /healthz, /readyz, /v1/media/*,
        /admin/extension*, /admin/cookie-helper, /admin/update/check
        and the console page itself requires
        Authorization: Bearer <API key>. The key is the one shown in the Account Pool tab;
        rotate it there if it leaks. API errors use {"error":{"message","type","param","code"}} for
        /v1/* and {"detail":"..."} for admin routes.

        About the tool-calling limitation: the muse.ai assistant refuses to emit fake tool-call JSON,
        so autonomous agent modes that depend on tool_calls (reading and writing files, running
        commands) cannot work. Everything question-and-answer shaped — chat, code, explanations, translation,
        summaries, images and videos — works. If a client insists on sending a tools array the request
        still succeeds: the tool declarations are ignored and the model answers as a normal conversation.
